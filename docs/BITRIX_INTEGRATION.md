# Интеграция с Битрикс24 (заявки → задачи)

Портал сам вызывает REST API Битрикса от имени **локального серверного приложения (OAuth)**. Входящий вебхук не используется.

## Как это работает
1. Администратор Битрикса создаёт приложение «HR-портал» и устанавливает его **от имени служебного пользователя**. Битрикс присылает токены на адрес установки (`/api/bitrix/install`). Портал проверяет токен у самого Битрикса, шифрует и сохраняет в таблице `BitrixConnection`, затем подписывается на событие `onTaskUpdate`.
2. Сотрудник подаёт заявку → `POST /api/requests` → после ответа сотруднику портал вызывает `tasks.task.add`. Номер задачи сохраняется в `Request.bitrixTaskId`.
3. HR меняет задачу в Битриксе → Битрикс шлёт `ONTASKUPDATE` на `/api/bitrix/events` → портал берёт актуальный статус задачи у Битрикса (`tasks.task.get`) и обновляет статус заявки.
4. Токен доступа живёт ~1 час, портал сам обновляет его по токену обновления (180 дней).

## Адреса приложения (для настройки в Битриксе)
| Поле в Битриксе | Адрес |
|---|---|
| Путь обработчика | `<АДРЕС_ПОРТАЛА>/api/bitrix/handler` |
| Путь для первоначальной установки | `<АДРЕС_ПОРТАЛА>/api/bitrix/install` |
| Обработчик событий (портал подписывается сам) | `<АДРЕС_ПОРТАЛА>/api/bitrix/events` |

Права приложения: `task`, `user`, `calendar`, `im`, `disk` (календарь, чат и диск пока не используются, но запрошены на будущее).

## Переменные окружения
| Переменная | Назначение |
|---|---|
| `BITRIX_DOMAIN` | адрес Битрикса, например `magssory.bitrix24.ru` |
| `BITRIX_CLIENT_ID` / `BITRIX_CLIENT_SECRET` | идентификатор и секрет приложения |
| `BITRIX_TOKEN_KEY` | длинная случайная строка для шифрования токенов в базе (не менять после установки без переустановки приложения) |
| `APP_URL` | публичный адрес портала (если не задан, используется `NEXTAUTH_URL`) |
| `BITRIX_HR_EMAIL` | email HR-сотрудника в Битриксе: исполнитель задач |
| `BITRIX_EXECUTOR_<ТИП>_EMAIL` | необязательно: другой исполнитель для типа заявки (`DOCUMENT`, `LEAVE`, `BUSINESS_TRIP`, `EQUIPMENT`, `ACCESS`), например `BITRIX_EXECUTOR_EQUIPMENT_EMAIL` |
| `BITRIX_GROUP_ID` или `BITRIX_GROUP_NAME` | группа для задач (по умолчанию ищется группа «Заявки HR») |
| `BITRIX_OAUTH_URL` | необязательно: адрес обновления токена (по умолчанию `https://oauth.bitrix.info/oauth/token/`) |

Пока `BITRIX_CLIENT_ID`, `BITRIX_CLIENT_SECRET`, `BITRIX_TOKEN_KEY` и `BITRIX_DOMAIN` не заданы, интеграция выключена и портал работает как раньше.

## Какие данные портал отправляет в задачу
Поля заявки (`Request`): тип (`DOCUMENT` справка, `LEAVE` отпуск/отгул, `BUSINESS_TRIP` командировка, `EQUIPMENT` техника, `ACCESS` доступ), статус (`PENDING`, `IN_PROGRESS`, `DONE`), комментарий сотрудника (`payload.description`), файлы (`files`: ссылка и имя), примечание (`note`), дата создания.
Данные сотрудника: ФИО, должность, отдел, email.

Задача в Битриксе:
- **Название:** `Тип — Фамилия И. (дд.мм.гггг – дд.мм.гггг)`, даты только если они переданы в `payload.startDate` / `payload.endDate` (сейчас форма отправляет один текстовый комментарий, поэтому даты пока не попадают в название).
- **Описание (BB-код):** тип заявки, сотрудник, отдел, даты, комментарий, примечание, файлы ссылками, ссылка на заявку в портале.
- **Исполнитель:** HR (`BITRIX_HR_EMAIL`), для отдельных типов — свой (`BITRIX_EXECUTOR_<ТИП>_EMAIL`).
- **Постановщик:** сам сотрудник (ищется в Битриксе по email). Если Битрикс не разрешает приложению ставить задачи от чужого имени, задача создаётся от имени приложения, а сотрудник указан в описании.
- **Группа:** «Заявки HR».

Соответствие статусов: Битрикс «новая» (2) и «отложена» (6) → «На рассмотрении», «выполняется» (3) и «ждёт контроля» (4) → «В работе», «завершена» (5) → «Готово».

## Проверить после подключения (код не проверялся на реальном Битриксе)
1. Установка приложения: в логах портала нет ошибок, в таблице `BitrixConnection` появилась запись.
2. Подача тестовой заявки создаёт задачу в группе «Заявки HR» с нужным исполнителем.
3. Смена статуса задачи в Битриксе меняет статус заявки (событие `onTaskUpdate` дошло до `/api/bitrix/events`).
4. Постановщик задачи — сотрудник (если нет, смотреть права приложения).
5. Формат запроса при установке: код принимает и `AUTH_ID/REFRESH_ID`, и `auth[access_token]`.

## Что можно сделать позже
- Передавать даты отпуска структурно (форма «Отпуск» с датами), чтобы название задачи содержало период.
- Закрывать задачу в Битриксе, когда HR меняет статус в портале.
- Повторная отправка заявок, для которых задачу создать не удалось (ошибки сейчас только в логах).
- Календарь: чтение встреч (`calendar.event.get`) и создание событий для отпусков (`calendar.event.add`).
